# 멀티게임 구조와 호환성

## ID와 등록

`roomId`는 지속되는 방, `gameId`는 그 방의 경기 회차 UUID, `gameType`은 `yacht`, `tikatuka`, `avalon`이다. 재경기는 `gameId`를 바꾸고 방 코드·게임 종류를 유지한다. 경기 중 다른 게임으로 변경하는 명령은 없다.

`src/shared/games.ts`가 이름·설명·인원·혼자 시작 방식의 공통 원본이다. 서버는 이 메타데이터로 시작 최소 인원과 참가 최대 인원을 확인한다. 공통 클라이언트는 해당 목록으로 카드·로비를 그린다. 자체 보드의 WebP 미리보기만 초기 화면에서 로드하며 게임 화면·도움말은 동적 import로 분리한다. Three.js와 게임 음향은 실제 게임 진입 때 로드한다.

| 게임 종류  | 인원        | 혼자 시작        |
| ---------- | ----------- | ---------------- |
| `yacht`    | 1–4명       | 1인 플레이       |
| `tikatuka` | 2명         | 컴퓨터 상대 추가 |
| `avalon`   | 사람 5–10명 | 없음             |

방 코드·초대 링크로 참가하면 서버가 확인한 `gameType`으로 이동한다. 아발론은 시작 후 고정 좌석과 역할을 유지하며 신규 참가자가 기존 자리를 대체하지 못한다.

## 모듈 경계

| 공통                               | 게임별                                  |
| ---------------------------------- | --------------------------------------- |
| 세션·닉네임·인증·권한              | 점수·역할·유효 행동과 수신자 정보       |
| 방 생성·참가·준비·시작·재경기·퇴장 | 초기 상태·시작·기권/무효·종료·상태 전이 |
| 연결·복구·기한·요청 큐             | 명령 의도·단계 범위와 저장 불변조건     |
| SQLite·영수증·속도 제한            | 화면·도움말·3D·오디오                   |
| 설정·오류·배포                     | 컴퓨터 판단                             |

공통 엔진은 회원 자격, 서버가 정한 게임 종류와 경기 ID를 확인한 뒤 게임에 맞는 명령 유효 범위를 적용한다. 야추·티카투카는 버전·턴·행위자·입력 가능 시각을 검사한다. 아발론은 같은 단계의 동시 제출을 허용하도록 단계·제안과 사용자별 제출 여부를 검사한다. 난수·시각·UUID 공급은 서버 내부 함수 인수이며 외부 API가 아니다. 공개 스냅샷, 게임의 비공개 상태와 참가 자격을 분리한다.

`RoomState`와 `Command`는 `gameType` 판별 유니온이다. 야추의 다섯 주사위·항목 점수, 티카투카의 보드·배치 단계·재굴림 후보, 아발론의 원정·투표·수신자 정보를 하나의 선택 필드 객체에 섞지 않는다. 티카투카 `stage`는 필요한 후보와 주사위의 존재 여부를 구별한다. 아발론은 `lobby/team/vote/quest/lady/assassination/finished` 단계별 권한과 저장 불변조건을 검사한다. 다음 게임을 추가할 때 공통 인증·방 코드를 복사하지 않고 메타데이터, 타입·검증, 순수 게임 모듈과 클라이언트 로더를 등록한다. 동적 실행이나 범용 플러그인 엔진은 두지 않는다.

아발론 타입·순수 규칙·프로젝션은 `src/shared/avalon.ts`, 서버의 공개 채팅·반응 처리는 `src/server/games/avalon.ts`에 있다. 게임별 화면은 자신의 렌더러·도움말·효과음을 소유한다. 공통 인증·SQLite·방 코드·배포 설정을 별도로 복제하지 않는다.

## 저장 형식 2

저장 형식은 `schemaVersion: 2`를 유지한다. 야추·티카투카 상태는 `protocolVersion: 2`, 아발론은 `protocolVersion: 3`이며 모두 `gameType`을 명시한다. 새 브라우저의 통신 지원 버전 3과 개별 게임 상태의 버전은 서로 다른 의미다. DO 클래스·바인딩과 SQL 테이블은 기존 그대로이고 JSON 레코드의 게임 종류와 버전으로 구별한다.

`migration.ts`는 실제 배포 커밋 `cdf76f06ae20f09eb10d24b73037440b3db5144b`의 SQLite에서 추출한 야추 fixture와 대조한다. 세 버전·종류 필드가 모두 없고 기존 키·규칙·점수·주사위·참가 데이터가 정확한 형식에 맞을 때만 야추로 이전한다. 당시의 주사위, 점수, 턴, 경기 ID, 자리, 기한과 요청 결과를 재계산하거나 다시 굴리지 않는다. 새 버전의 메타데이터와 사람 좌석 종류만 추가한다.

알 수 없는 종류, 일부 버전만 있는 형식, 손상된 점수·주사위·후보와 모순된 회원 정보는 원본을 보존하고 오류로 중단한다. 컴퓨터가 행동할 저장 상태에는 실행 기한이 반드시 있어야 한다. 모든 비정상 레코드를 야추로 간주하거나 새 경기로 초기화하지 않는다. 기존 요청 영수증은 응답 시 버전 메타데이터를 보완하고 최초 확정 결과를 유지한다.

아발론은 내부 저장용 `InternalRoomState`와 통신용 `RoomState`를 별도 유니온으로 둔다. `migrateStoredRoom`은 `isAvalonInternalState`로 내부 형식을, 공개 상태·요청 영수증은 `isAvalonRoomState`로 수신 형식을 검사한다. 내부 `secrets`가 들어 있는 객체를 공개 영수증으로 받아들이지 않는다. 역할 구성, 고정 좌석, 대장 순환, 제안·투표·원정 기록의 관계, 자기 제출과 조사 결과, 정상 종료와 무효 종료를 검증한다.

## 아발론의 수신자 경계와 동시성

| 타입                  | 전달 범위                                                                  |
| --------------------- | -------------------------------------------------------------------------- |
| `AvalonInternalState` | 서버 SQLite. 역할·미집계 제출·조사 결과를 포함한다.                        |
| `AvalonPublicState`   | 모든 참가자가 공유하는 정보. 3D 보드에는 이 형식만 전달한다.               |
| `AvalonRoomState`     | 공개 정보와 해당 수신자의 `privateInfo`. HTTP·WebSocket·오류·영수증용이다. |

프로젝션은 중첩 객체까지 명시적인 허용 필드로 새로 만든다. 수신자의 역할별 인물 목록은 상세 동료 역할과 구분하며, 방장에게 추가 권한을 주지 않는다. 다른 사람의 미집계 찬반·원정 카드, 역할 패널 열기와 개인 메모를 보내지 않는다. 전원 투표 후 개인 찬반은 공개하지만 원정은 성공·실패 수와 판정만 남긴다. **원정 집계 직후 내부 작성자별 카드 맵도 삭제**하며 작성자에 연결되는 카드 ID·배열·순서가 없다. 이전 자기 제출 영수증은 요청한 신원에게만 그대로 반환하고 현재 `myQuestCard`는 집계 후 비운다.

아발론 규칙 명령은 경기 ID에 더해 `phaseId`와 `proposalId`를 요구한다. 동일 단계에서 다른 사람의 제출·채팅·접속 표시가 바뀌어도 자기 미제출 행동은 유효하다. `expectedVersion`은 전송되지만 이 게임의 동시 제출을 거절하는 기준으로 사용하지 않는다. 이미 제출한 사람의 새 요청, 다른 단계·제안 요청은 거절한다. 마지막 제출의 기록과 집계, 다음 단계, 성공 영수증은 하나의 SQLite 트랜잭션에 저장한다.

`phaseId`는 단계 또는 설정이 바뀔 때 갱신하고 공통 `turnId`와 같은 값을 쓴다. 아발론의 공통 `ready/start/rematch`는 이 단계 값에 바인딩된다. 역할·옵션 변경은 전원의 준비를 해제하여 변경 전 준비 요청이 늦게 도착해도 새 구성을 승인하지 못하게 한다. 원정대 초안과 카드·투표의 제출 전 선택은 클라이언트 로컬 상태다. 채팅·공개 반응은 경기 ID만 바인딩하여 토론 중 단계 변경으로 입력을 잃지 않게 한다.

아발론 채팅은 300자까지이며 최근 100개를 보관한다. 같은 발신자의 동일 내용은 5초 내 중복을 거절하고 참가자당 분당 30회·800ms 버킷당 1회로 제한한다. 반응은 최근 30개, 분당 12회·1,500ms 버킷당 1회다. SQLite에 제한을 저장하며 같은 성공 요청 재전송은 발언이나 반응을 추가하지 않는다. 공개 규칙 기록과 사용자의 주장은 별도로 보관한다.

## 재전송과 컴퓨터

상태 갱신, 난수 결과, 속도 제한과 성공 영수증은 `transactionSync` 하나에서 커밋한다. 알까기 제거와 이미 생성한 실드 보너스, 재굴림 자원과 두 후보는 각각 하나의 트랜잭션 결과다. 성공 영수증을 버전 검사 전에 조회하여 같은 요청을 다시 보내도 눈이나 자원이 달라지지 않는다.

티카투카의 선언 규칙은 원작 근거가 미확정이므로 임의의 승패 전이를 활성화하지 않는다. 확인한 원작 규칙과 미확정 내용은 기존 티카투카 규칙 문서를 유지한다. 아발론 원작 근거와 웹의 운영 정책은 [아발론 규칙](avalon-rules.md)에 별도로 구분한다.

컴퓨터에게 세션·회원 인증값은 발급하지 않는다. 공개 상태만 받는 제한된 평가 함수가 합법 행동을 선택한다. 생성 전 눈을 읽지 않고 가능한 눈의 기댓값을 비교하며 실제 실행은 사람과 같은 RNG·전이 함수를 사용한다. 현재 턴·버전으로 만든 내부 요청 ID와 저장된 `aiDueAt`을 기준으로 Alarm이 한 단계씩 커밋한다. 재시작과 중복 Alarm은 이미 처리한 차례를 다시 실행하지 않는다. 사람이 모두 나가면 컴퓨터가 방의 수명을 계속 늘리지 않는다.

컴퓨터 상대는 티카투카에만 적용한다. 아발론은 사람의 역할·좌석을 컴퓨터로 대체하지 않는다. 세 게임 모두 참가자당 경기 전체에서 누적 120초의 연결 유예를 사용한다. 아발론은 이 예산이 소진되거나 진행 중 명시적으로 퇴장·세션 폐기하면 전체 경기를 무효 종료하고 승리 진영이나 전체 역할을 공개하지 않는다. 재경기는 남은 참가자의 새 로비에서 시작한다. 방당 연결 상한은 교체 중인 소켓을 포함해 야추·티카투카 8개, 아발론 20개이며 참가자별 활성 연결은 하나다.

## 화면 수명

카탈로그 탐색은 게임 화면·장면·게임 효과음 AudioContext를 정리하지만 연결과 좌석을 유지한다. 공통 BGM 컨텍스트는 유지하면서 로비 음악으로 교차 페이드한다. 돌아가기는 현재 서버 방의 게임을 연다. 다른 카드를 고른 것만으로 게임 종류를 바꾸거나 기권하지 않는다. 다른 방 시작과 명시적 퇴장은 확인 후 공통 퇴장 명령을 사용한다. 기존 닉네임·설정·세션 저장 키는 유지한다.

카드 WebP는 이 프로젝트의 절차적 보드를 캡처한 자산이다. 원작 게임의 텍스처·로고·음원을 게임 번들에 포함하지 않는다. 원작 관찰은 규칙과 배치의 참고 자료로만 기록한다.

## 이전 브라우저와 통신 협상

새 클라이언트는 HTTP의 `X-Game-Protocol: 3`, WebSocket URL의 `protocolVersion=3`으로 지원 버전을 알린다. 이는 공개 호환성 메타데이터이며 인증 정보가 아니다. 쿠키·Origin·CSRF 검증은 그대로 유지한다. WebSocket attachment에도 지원 버전을 저장해 재개 후 방송에 적용한다.

| 브라우저가 알린 지원 버전 | 야추           | 티카투카  | 아발론    |
| ------------------------- | -------------- | --------- | --------- |
| 표식 없음                 | 기존 동작 유지 | 갱신 안내 | 갱신 안내 |
| 2                         | 유지           | 유지      | 갱신 안내 |
| 3                         | 지원           | 지원      | 지원      |
| 그 외 명시 버전           | 갱신 안내      | 갱신 안내 | 갱신 안내 |

표식 없는 기존 클라이언트는 야추 생성·참가·상태 조회·WebSocket과 기존 명령을 계속 사용한다. 버전 2 클라이언트의 야추·티카투카 상태와 명령도 유지한다. 아발론에는 최초 참가·조회·WS 설치 전에 버전 3을 요구한다. 호환되지 않는 요청은 `PROTOCOL_REFRESH`를 반환하며 자격·자리·경기·기존 연결을 바꾸지 않는다. 오류 응답과 방송에도 해당 게임 상태를 첨부하지 않는다. 새 버전으로 새로고침하면 기존 세션과 방을 복구한다.

명령 자체의 게임 종류·버전 검사도 별도로 유지한다. 새 화면으로 새로고침한 뒤 아직 해결되지 않은 기존 야추 요청이 남아 있으면 원래 직렬화한 요청 ID·내용을 그대로 재전송한다. 한 번도 보내지 않은 다른 게임의 선택만 큐에서 제거한다.

## 실행한 경계 검증

아발론 순수 규칙과 정보 비노출 테스트, SQLite 동시 제출·원자 롤백·재열기·수신자 영수증 테스트를 통과했다. 실제 로컬 workerd의 `tests/browser/avalon-protocol.spec.ts`에서는 정상 다섯 게스트로 준비·시작·혼합 HTTP/WS 투표·익명 원정 집계를 진행했다. 버전 누락·2의 참가/조회/WS 거절이 방 상태나 연결을 바꾸지 않고, 성공·오류·재전송·방송의 `privateInfo`가 자기 신원에만 속하며 공개 부분은 모두 같은 것을 확인했다.

`scripts/avalon-persistence.mjs`는 격리된 로컬 SQLite와 실제 workerd를 부분 투표·부분 원정·최종 집계에서 세 차례 재시작한 검사를 통과했다. 역할과 자기 제출·원래 영수증 복구, 마지막 제출의 단일 집계, 원정 작성자 맵 삭제를 확인했다. 기존 야추 fixture 이전 및 야추·티카투카 재시작 검사도 별도로 유지한다. 전체 실행 결과와 UI·배포 증거는 `docs/verification.md`를 따른다.
