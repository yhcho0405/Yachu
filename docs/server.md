# 서버, 인증과 온라인 확장 정책

## 단일 출처와 저장 경계

`wrangler.jsonc`만 인프라 설정의 원본으로 사용한다. `dice-atelier` Worker는 Vite 빌드 자산, `/api/*`, WebSocket을 같은 `workers.dev` 출처에서 제공한다. `/api/*`와 비공개 내부 경로는 `run_worker_first`로 SPA fallback보다 먼저 처리한다. 없는 API는 JSON 404다. Static Assets의 직접 응답은 `public/_headers`, Worker 응답은 `src/server/response.ts`에서 CSP·프레임 차단·nosniff·Referrer Policy를 적용한다. 정적 헤더는 실제 브라우저 검사에서 확인한다.

`ROOMS` 바인딩의 `GameRoom` 하나가 방 하나의 권위 서버다. `REGISTRY`의 `SessionRegistry`는 게스트 자격증명 해시, 방 코드 조회, 인증/생성/참가/연결 속도 제한과 세션 폐기를 위한 방 참조만 관리한다. 두 클래스 모두 SQLite 기반 Durable Object이며 최초 `v1` 마이그레이션으로 생성한다. D1, KV, 외부 데이터베이스, Pages, 별도 Node 게임 서버를 사용하지 않는다. 이후 배포에서도 클래스와 네임스페이스를 유지한다.

## 게스트 인증

- 32바이트 암호학적 난수 토큰을 서버에서 발급한다. 브라우저 쿠키는 `__Host-dice_session`, `Path=/`, `HttpOnly`, `Secure`, `SameSite=Strict`다. 인증 토큰은 URL·localStorage·로그에 기록하지 않는다.
- Registry에는 원본 토큰 대신 `SESSION_SECRET`을 사용하는 HMAC-SHA-256 해시를 저장한다. CSRF 토큰과 IP 제한 키는 목적 문자열이 다른 HMAC으로 분리한다. 닉네임은 1–16자 NFC 문자열이고 신원이 아니다. 같은 닉네임도 무작위 `playerId`가 다르면 다른 참가자다.
- 세션은 발급 후 7일 동안 유효하고 자동 연장하지 않는다. `DELETE /api/session`은 Registry 폐기를 먼저 저장하고 관련 방의 참가 권한과 연결도 폐기한다. 방에는 폐기 표식을 저장해 참가/재접속과 폐기의 경쟁에서도 폐기된 세션이 다시 들어오지 못하게 한다. 폐기 표식은 7일 뒤 정리한다.
- 유효한 쿠키로 `POST /api/session`을 다시 호출하면 현재 세션을 반환한다. 닉네임은 해당 자격증명에서 변경하지 않는다. 새 신원은 세션 폐기 후 생성한다.
- 모든 HTTP 변경은 정확한 현재 출처의 `Origin`을 요구한다. 인증된 변경에는 `X-CSRF-Token`도 필요하다. WebSocket은 동일한 쿠키와 정확한 `Origin`으로 인증하며 각 명령마다 Registry에서 만료/폐기를 다시 확인한다. 장기 토큰을 URL에 넣는 WebSocket 티켓은 사용하지 않는다.
- `SESSION_SECRET`이 없거나 UTF-8 32바이트 미만이면 인증/건강 검사에 503을 반환한다. 인증 생략이나 기본 운영 비밀값은 없다. 로컬 실행에서만 별도 난수를 생성해 무시되는 `.dev.vars`에 저장한다.

8자리 방 코드는 혼동하기 쉬운 문자 I/O/0/1을 제외한 32개 문자로 만든 40비트 난수다. 방 ID는 별도의 암호학적 UUID다. 방 코드는 생성 후 7일 만료하고, 방 자체는 더 일찍 정리될 수 있다. 코드 조회/참가 시도를 지속 저장된 버킷으로 제한한다. 코드를 알아도 기존 자리를 복구하거나 비참가자로 점수판을 조회할 수 없다. 세션과 방에 등록된 참가 권한이 함께 있어야 한다.

## 상태 전이와 원자성

상태 전이는 `lobby → playing → finished → lobby`다. 재경기는 새로운 `gameId`를 부여하고 기존 참가자들의 점수를 비운 대기실을 연다. 방장 시작 시 다른 참가자들은 모두 준비되어 있어야 하고 모두 연결되어 있어야 한다. 혼자 시작하는 방장에게 별도 준비 버튼은 요구하지 않는다. 시작 후 신규 선수는 들어올 수 없다. 로비 참가 검증과 저장은 같은 동기 SQLite 트랜잭션 안에 있어 마지막 자리에 동시에 참가해도 게임별 최대 인원(야추4, 티카투카2)을 넘지 않는다. 티카투카는 두 좌석이 있어야 시작하며 혼자 시작은 인증 자격이 없는 컴퓨터 좌석을 추가한다.

서버가 주사위·보관 상태·점수·보너스·차례·순위와 모든 ID를 관리한다. 공통 의도는 `ready/start/rematch/leave`다. 야추는 `hold/roll/score`, 티카투카는 배치·재굴림·후보 선택·홀드의 게임별 의도만 전송한다. 게임 종류와 프로토콜에 맞지 않는 명령은 적용하지 않는다. 스키마는 허용 필드만 받으며 사용자 ID, 주사위 값, 점수, 승자를 주입하는 API는 없다. 상태 크기, 타입, 정수 범위, 다섯 개 불리언 보관 배열과 항목 이름을 검사한다. HTTP/WS 메시지는 JSON 파싱 전에 UTF-8 4,096바이트로 제한하고 이진 WS 명령은 거절한다. SQL 값은 바인딩된 매개변수를 사용한다.

`RoomStore.process`의 처리 순서는 다음과 같다.

1. 외부 Registry에서 현재 세션을 확인한다.
2. 동기 `transactionSync` 안에서 방의 폐기 표식과 해당 신원의 세션 바인딩을 확인한다.
3. `(playerId, gameId, requestId)`로 이미 성공한 요청을 조회한다. 필드 순서와 관계없이 같은 내용이면 저장한 응답을 그대로 반환한다. 같은 ID를 다른 내용에 사용하면 `REQUEST_ID_REUSED`다.
4. 처음 보는 요청은 현재 참가 권한, 경기 ID, `expectedVersion`, 필요한 `turnId`, 차례와 게임 사전조건을 검증한다. 오래된 새 요청은 최신 상태와 함께 거절한다.
5. DB에서 새로 읽은 객체만 변경하고 버전을 증가시킨다. 방 상태와 성공 응답 기록을 같은 SQLite 트랜잭션에 저장한다. 도중 예외가 나면 둘 다 롤백한다.
6. 저장 동기화가 성공한 뒤 요청 응답과 전체 스냅샷을 전송한다. 메모리의 상태를 먼저 진행시키는 캐시는 없다.

중복 확인이 버전 확인보다 먼저여서 응답이 유실된 굴림을 재전송하면 최초 확정된 주사위를 되돌려준다. 탈퇴와 재경기의 성공 응답도 같은 방식으로 복구한다. 폐기된 세션은 이전 성공 기록도 조회할 수 없다. 실패한 명령은 상태를 변경하지 않고 성공 기록을 만들지 않는다. 새 선택은 새 `requestId`를 사용한다.

난수는 `crypto.getRandomValues`의 32비트 값을 사용하고 6으로 나눠떨어지지 않는 범위의 마지막 네 값을 버리는 rejection sampling으로 편향을 제거한다. 시간·UUID·주사위 공급 주입은 독립적인 엔진 테스트의 함수 인수에만 존재한다. 운영 HTTP/WS에는 강제 값이나 시간 조작 경로가 없다.

굴림 결과는 저장 후 바로 확정된다. 야추의 다음 입력은 서버 시각 기준 1초 뒤에 가능하다. 티카투카도 저장한 단계별 입력 시각을 사용하며 공격 제거와 새 보너스는 함께 확정한다. 클라이언트의 애니메이션 완료를 기다리지 않는다. 클라이언트는 이 확정 값을 향해 주사위를 연출하며, 과거 응답은 최신 경기/버전을 덮어쓰지 않도록 관리한다.

## 연결, 이탈과 재접속

`version`은 게임/로비 변경, `presenceVersion`은 연결 표시 변경이다. 단순 접속 알림은 게임 명령의 `expectedVersion`을 무효화하지 않는다. 일반 상태 조회는 해당 요청에만 응답하고 다른 참가자에게 불필요하게 재방송하지 않는다.

`acceptWebSocket`과 attachment에 저장한 `playerId`, 해시된 세션 식별자, 연결 ID, 만료 시각을 사용하여 하이버네이션을 지원한다. 게임 상태는 attachment나 메모리가 아닌 SQLite에 저장한다. 객체 재생성 때 살아 있는 attachment와 DB 연결 ID를 대조하고 사라진 연결에 유예를 시작한다. 하이버네이션을 막는 상시 타이머가 없으며 필요한 기한에만 Alarm을 예약한다. `ping/pong`은 자동 응답으로 처리할 수 있다.

한 참가자는 최신 WebSocket 하나를 사용한다. 새 연결 설치 구간을 직렬화하고 이전 연결에 교체 안내를 보낸 뒤 닫는다. 이전 연결의 close/error는 연결 ID가 현재 ID와 같을 때만 끊김으로 반영한다. 방에서 종료 중인 연결까지 포함하여 8개를 넘으면 새 연결을 잠시 거절한다. 같은 신원의 HTTP는 계속 동일한 참가 권한을 사용하지만 클라이언트는 교체된 탭의 조작을 멈춘다.

온라인 확장은 원작 규칙과 별개다.

- 야추1–4인, 티카투카2인 경기. 방장은 대기실 시작/재경기 권한만 가지며 경기 결과나 타인의 차례를 바꾸지 못한다.
- 연결이 유지되는 차례에 짧은 자동 턴 제한을 두지 않는다. 방에는 아래 24시간 무활동 정리 정책이 적용된다.
- 로비 연결이 끊기면 120초 기다린 뒤 자리를 제거한다. 방장이 제거되면 연결된 남은 참가자 우선, 다음으로 좌석 순서에 따라 위임한다.
- 경기 중에는 한 참가자의 **전체 경기에서 누적 120초**까지 끊김을 허용한다. 돌아오면 사용한 시간을 남은 예산에서 차감하고 다시 끊기면 잔여 시간만 준다. 반복 접속으로 예산이 복구되지 않는다. 재경기에만 새 예산을 부여한다.
- 기한 정각부터 재접속보다 만료가 우선한다. Alarm이 지연되어도 새 요청이 저장된 기한을 먼저 검사한다. 중복 Alarm은 이미 처리한 기권을 반복하지 않는다.
- 명시적인 퇴장은 로비에서는 즉시 좌석 제거, 진행 중에는 즉시 기권이다. 이미 기록한 점수는 유지한다. 야추는 기권자를 정상 완주자 뒤에 정렬하고 다음 유효 참가자로 진행한다. 모두 항목을 마치거나 기권하면 결과를 확정한다. 티카투카는 즉시 상대의 기권승으로 종료하고 실제 보드 점수를 보존한다.
- 완료된 경기의 결과는 퇴장으로 다시 계산하지 않는다. 동점은 공동 순위(예: 1, 1, 3)다. 같은 방의 재경기는 남아 있는 참가자들과 새 대기실을 연다.

## 저장 수명과 제한

방은 마지막 게임/로비 변경 후 24시간 동안 보존한다. 단순 스냅샷 조회나 접속 알림은 수명을 늘리지 않는다. 모든 사람 참가자가 명시적으로 나가거나 유예가 만료되면 120초 안에 방과 요청 기록을 정리한다. 그 방의 코드 매핑은 Registry의 7일 만료 때 지워지며 그 전에도 방 조회는 404다.

현재 경기의 성공 요청 기록은 방이 없어질 때까지 유지한다. 이전 경기 기록은 최소 24시간 뒤 다음 정리 Alarm에서 삭제하며, 삭제 후 옛 경기의 요청은 `gameId`가 달라 거절된다. 요청 기록은 방당 최대 50,000건으로 제한한다. 이후 기록을 수용하지 못할 때 새 방을 안내한다. 한도를 넘었다고 아직 유효한 중복 기록을 임의 삭제하지 않는다.

Registry의 세션·코드·방 참조와 속도 버킷은 시간 단위 Alarm으로 정리한다. 제한은 Worker 메모리가 아닌 SQLite에 저장한다. 기본 한도는 인증 IP당 분당 60회, 생성 세션당 시간당 6회/IP당 30회, 참가 세션당 분당 30회/IP당 60회, WS 재접속 세션당 분당 30회다. 인증된 HTTP는 세션당 분당 360회, WS 명령은 분당 240회로 제한한다. 방 안의 성공 명령도 참가자당 10초에 60회/방당 180회로 제한한다. 전체 게임을 정상 속도로 하는 데 필요한 한도보다 충분히 크게 설정했다. 무료 무제한 운영을 가정하지 않으며 Registry는 소규모 친구 게임을 위한 단일 조정 지점이다.

## SQLite 스키마와 마이그레이션

실제 SQL 초기 스키마는 `src/server/store.ts`와 `src/server/registry.ts` 생성자에 있다. `CREATE TABLE IF NOT EXISTS`와 명명된 인덱스로 재시작에 안전하게 초기화한다. 새 배포에서 기존 테이블을 삭제하지 않는다.

| 객체            | 테이블                                                                    | 역할                                                          |
| --------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------- |
| GameRoom        | `room(singleton, data)`                                                   | 공개 스냅샷과 비공개 참가 바인딩/연결/예산의 원자 JSON 레코드 |
| GameRoom        | `requests(player_id, game_id, request_id, payload, response, created_at)` | 복합 기본키의 성공 요청 및 최초 응답                          |
| GameRoom        | `rate_limits(key, window_start, count)`                                   | 방/참가자의 입력 제한                                         |
| GameRoom        | `revoked_sessions(key, expires_at)`                                       | 세션 폐기와 재참가 경쟁을 막는 영속 표식                      |
| SessionRegistry | `sessions(key, player_id, nickname, expires_at, revoked)`                 | 토큰의 목적별 HMAC 해시와 세션 만료/폐기                      |
| SessionRegistry | `codes(code, room_id, expires_at)`                                        | 난수 코드의 유일한 방 매핑                                    |
| SessionRegistry | `rates(key, window_start, count)`                                         | 전체 인증/생성/참가/연결 제한                                 |
| SessionRegistry | `session_rooms(session_key, room_id, expires_at)`                         | 폐기 시 해당 방에 전달하기 위한 참조                          |

SQL DDL의 `v1` 구조는 `wrangler.jsonc`의 `new_sqlite_classes` 초기 마이그레이션에 대응한다. 이후 컬럼 변경은 별도 스키마 버전으로 순방향 마이그레이션하고, 이미 배포한 `v1` 태그를 변경하거나 클래스 이름을 바꾸어 저장소를 재생성하지 않는다. 배포 롤백 시에도 기존 데이터 형식과 호환되는 코드를 선택한다.

## 확인한 근거와 실행한 검증

Cloudflare 공식 [SQLite 저장소](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/), [WebSocket Hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/), [Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/) 문서를 확인했다. 동기 트랜잭션 안에는 외부 I/O와 `await`를 두지 않으며 SQL 커서를 await 이후에 이어서 읽지 않는다. `blockConcurrencyWhile`의 예상 거절은 내부에서 응답으로 바꿔 불필요한 객체 재시작을 막는다.

기존 야추 서버·규칙 검사를 유지하며 티카투카와 호환성·복구 검사를 추가한다. 현재 실행 결과는 `docs/verification.md`에 기록한다. 기존 검사는 전체 7,776개 주사위 조합, 독립적인 조합 개수, 최고점 325, 1–4인 완주와 재경기, 참가 권한/턴/버전, 누적 유예와 오래된 close, 중복 Alarm, SQLite 파일을 닫고 다시 연 복구, 저장 실패의 원자 롤백, 동일 요청 재전송과 중복 점수 확정, strict 스키마/Origin/본문 크기/HMAC/편향 없는 난수를 포함한다. 실행 환경은 로컬 Node.js 26, Vitest 5이며 CI는 Node.js 24를 사용한다.

`tests/browser/server-api.spec.ts`는 실제 로컬 Wrangler/workerd에 다섯 개의 독립 Chromium 쿠키 컨텍스트로 접속하여 같은 닉네임의 별도 신원, 동시 마지막 자리 참가, WebSocket 명령과 방송, CSRF/Origin/비참가자/상대 차례 거절, 중복·오래된 버전·이전 경기·재사용 ID, 보관/굴림 경쟁, 점수 중복, 연결 교체, 세션 폐기와 방장 위임을 통과했다. 이 방어 검사는 로컬에서만 실행하고 실서비스에서는 건너뛴다. 브라우저 trace와 HAR는 저장하지 않는다. 실제 브라우저 쿠키 보안 동작은 UI 테스트에서 검증하며, APIRequestContext의 로컬 HTTP Secure-cookie 차이는 해당 테스트가 자기 세션 쿠키를 명시적으로 전달하여 처리한다.

`scripts/persistence.mjs`는 별도 로컬 SQLite 디렉터리와 실제 Wrangler 프로세스를 중지/재시작하여 세션, 자리, 주사위, 버전, 차례와 최초 응답 복구를 확인했고 통과했다. 추가로 workerd가 정지한 동안 이 격리된 임시 DB의 단 하나인 테스트 세션을 만료시키고 재시작하여, 정상 세션 조회와 이전 방 조회가 모두 401이고 방 스냅샷을 포함하지 않는 것을 확인했다. 운영 API에 시간이나 인증을 조작하는 경로를 추가하지 않았다. 전체 UI와 배포 후 정상 멀티플레이의 실행 결과, 남은 검증 제한은 `docs/verification.md`에 별도로 기록한다. 단위 검사의 시각 주입과 재시작 검증을 실제 Cloudflare 하이버네이션 강제 발생이나 실기기 측정으로 표현하지 않는다.

## 멀티게임 확장의 저장 경계

게임 종류와 스키마·프로토콜 버전은 공개 상태에 포함한다. 실제 기존 야추 형식만 메타데이터를 추가해 이전하며 저장된 눈·점수·자리·경기와 최초 영수증은 보존한다. 손상 또는 알 수 없는 형식은 데이터를 그대로 둔 채503으로 거절한다. SQL 테이블과 기존 DO 마이그레이션 이력은 바꾸지 않는다. 자세한 ID·모듈·레거시 처리 방식은 [멀티게임 구조](multigame.md)에 있다.

티카투카는 공격자 소모·상대 제거·이미 생성된 실드 보너스를 한 상태로 저장한다. 재굴림을 쓰면 사용 자원과 기존·새 후보를 함께 저장하고 선택을 따로 확정한다. 단순 재접속·재전송으로 후보와 보너스를 다시 생성하지 않는다. 게임별 validator는 칸수·고유 주사위 ID·점수·행위자·세부 단계·자원·결과를 검사한다. 선언의 실제 규칙은 미확정이므로 임의 전이를 두지 않는다.

컴퓨터에게는 회원 자격이나 세션을 발급하지 않는다. 서버의 공개 상태 평가로만 합법 의도를 고르고, 방 저장소의 내부 트랜잭션에서 실행한다. 저장된 실행 기한과 턴/버전별 영수증은 재시작 또는 반복 Alarm에서도 한 단계만 커밋하게 한다. AI 단계에는 외부 I/O와 무한 탐색이 없다. 사람과 같은 RNG·배치 제한을 사용하고 게임 종료·전원 퇴장 시 AI 예약을 없앤다.

추가 검사는 `tests/tikatuka.test.ts`, `tikatuka-store.test.ts`, `multigame.test.ts`, `migration.test.ts`에 있다. `scripts/tikatuka-persistence.mjs`는 별도 실제 workerd를 중지하고 재실행하여 공격 직후 보너스·재굴림 후보·원래 후보 선택·최초 영수증 및 컴퓨터 실행 예약의 복구를 검사한다. 임시 로컬 상태만 사용하며 운영 조작 경로는 추가하지 않는다.
